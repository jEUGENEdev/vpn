# Границы защиты

## Маршрутизация

| Состояние адреса | Канал | При ошибке VPN |
|---|---|---|
| Не одобрен | Прямое соединение из службы | Остаётся прямым |
| Одобрен | VLESS → XHTTP → REALITY | Блокируется, прямого fallback нет |
| Неизвестный адрес из Fake-IP диапазона | Запрет | Запрет |

Публичные суффиксы (`com`, `co.uk`, `github.io`), wildcard, URL, порт и CIDR не принимаются как разрешение. Сравнение выполняется по границе DNS-меток. `example.com` не разрешает `evil-example.com`. Unicode нормализуется через IDNA, IPv4-mapped IPv6 приводится к IPv4.

Xray на сервере по умолчанию направляет всё в blackhole. Разрешающие правила привязаны к VLESS-пользователю конкретного устройства. Сервер дополнительно проверяет реальные IP перед исходящим соединением и запрещает внутренние сети, localhost, link-local, metadata, multicast и переходные IPv6-префиксы. Поэтому разрешение домена не даёт доступ к внутренней инфраструктуре VPS через DNS rebinding.

Нажатие «Одобрить» сначала сохраняет локальную защиту и закрывает соответствующие прямые соединения, затем отправляет запрос серверу. Даже если API не ответил, адрес не возвращается к direct: локальная защита остаётся до успешного одобрения или явного удаления. Смена политики закрывает старые соединения. При неудачной синхронизации последняя сохранённая политика не превращается в пустой список; одобренные адреса остаются заблокированными. Серверные изменения применяются через остановку старого Xray перед запуском нового: сбой конфигурации оставляет data plane закрытым.

## DNS и наблюдаемость

Клиент перехватывает обычный DNS (TCP/UDP 53), возвращает стабильные Fake-IP для A/AAAA и хранит соответствия на диске. Даже после перезапуска старый Fake-IP не получает другой домен. Удаление DNS-базы при сохранённых кэшах не приводит к прямому соединению: неизвестные Fake-IP блокируются. HTTPS/SVCB DNS-ответы не передают ECH/IP-подсказки, DoT на 853 блокируется.

**Существенное ограничение:** произвольный DoH внутри HTTPS, собственный DNS приложения, встроенные IP и DNS-кэши до запуска клиента могут скрывать доменное имя. Неизвестный реальный IP по требованиям пользователя идёт напрямую. Нельзя одновременно гарантировать определение скрытого домена в любом зашифрованном потоке и автоматически разрешать все неодобренные IP напрямую. Для доменных гарантий приложения должны использовать DNS клиента; отключите Secure DNS/DoH в приложениях. Одобренный IP защищается независимо от DNS. Обходы должны быть проверены на целевых приложениях до production; этот проект не выдаёт отсутствие утечек для произвольного внешнего DNS за доказанный факт.

Синхронизация политики между устройствами происходит каждые 5 секунд при доступном API. Новое одобрение с другого устройства защищает домен после получения новой версии. Офлайн-устройство не может узнать о новом правиле до восстановления связи. Строго одновременная активация на всех устройствах потребует отдельного протокола lease/ack и не заявляется в preview.

## Защита при падении

Android полагается на явно включённый системный lockdown. Windows использует persistent WFP, macOS — PF anchor и отдельный UID. При падении фоновой службы может блокироваться вся сеть. Проверка конкретного сетевого стека, загрузки ОС, DHCP, IPv6, смены интерфейса, существующих соединений и совместимости с другими firewall обязательна по `acceptance.md`. Наличие правил в коде не является доказательством, что ни одна платформа не пропускает пакеты.

## Сервер и инфраструктура

REALITY защищает клиентский канал, собственный HTTPS-домен не требуется. API использует TLS 1.3 с закреплением SPKI публичного ключа. В коде включён `InsecureSkipVerify` только вместе с обязательным `VerifyConnection`, проверяющим ключ и срок сертификата; пустой/чужой pin отклоняется. Перенаправления HTTP запрещены.

Пароли аккаунтов хранятся как bcrypt; токены устройств и коды привязки — SHA-256 от случайных 256-/120-битных секретов. Админ-пароль задаётся через Ansible Vault, на сервере читается из файла 0600; сессия администратора живёт восемь часов и хранится в памяти. Admin/API не используют cookies, все изменения требуют bearer-токен. Пароли и ключи не пишутся в access log; журналы посещений Xray отключены. База хранит разрешения и очередь запросов, поэтому резервные копии конфиденциальны.

VPS-провайдер всё равно может видеть IP-адреса, объём и время соединений; оператор гипервизора потенциально видит память/диск VM. Исходящий HTTP к сайту не шифруется магически после выхода из VPN. Ни REALITY, ни этот проект не обещают невидимость для владельца VPS или защиту от компрометации серверной ОС.
