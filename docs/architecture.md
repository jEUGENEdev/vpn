# Архитектура

- `internal/policy`: нормализация адресов, наследование доменов, решение direct/VPN/block.
- `internal/client`: устойчивая DNS-таблица, TUN TCP/UDP, политика и синхронизация, локальный API.
- `internal/transport`: закреплённая версия Xray, VLESS/XHTTP/REALITY, запрет private egress и обязательный socket protect/bind.
- `internal/server`, `internal/store`: аккаунты, регистрационные заявки, устройства, одноразовая привязка, разрешения, BoltDB.
- `internal/events`: ограничение частоты уведомлений и группировка доменов.
- `internal/platform`: постоянная защита WFP/PF, TUN и привязка исходящих сокетов к физическому интерфейсу; восстановление прямого доступа при явном выключении или удалении.
- `internal/ui`: встроенный интерфейс клиента и админки без внешних CDN/шрифтов/аналитики.
- `apps/desktop`: Electron UI; фоновая служба существует независимо от окна.
- `apps/android`, `mobile`: Android VpnService, уведомления и JNI/gomobile.
- `deploy/ansible`: воспроизводимый деплой Linux-сервера без домена.
- `scripts`, `packaging`, `.github/workflows`: платформенные сборки и комплект установщиков.

## Разработка

Go 1.27.4, Node 24, Java 17, Android SDK 35 / NDK 28.0.13004108 / Gradle 8.11.1. Мобильный клиент использует Android 10+.

```bash
go test -race -tags with_gvisor ./...
go vet -tags with_gvisor ./...
scripts/build-server.sh
```

Проверки интерфейса без системного браузера и полный браузерный прогон:

```bash
npm ci --prefix tools/ui-tests --ignore-scripts --no-audit --no-fund
tools/ui-tests/node_modules/.bin/playwright install chromium
bash scripts/check.sh ui
```

DOM-проверки исполняют настоящий код клиента и админки с тестовыми данными: источники событий, поиск, сохранение состояния строк и адреса действий. Они не проверяют визуальную раскладку; для неё нужен полный прогон Playwright.

Общий локальный прогон, security checks и правила ревью описаны в
[проверках безопасности и качества](security-quality.md); инструкции для агентов
находятся в корневом `AGENTS.md`.

Интеграционный тест транспортного слоя поднимает настоящий Xray-клиент и сервер с XHTTP/REALITY и проверяет TCP/UDP round trip, затем удаляет разрешение и проверяет отсутствие соединений к целевому listener. Интернет и реальный VPS для этого теста не нужны.

Нативные команды сборки: `scripts/package-android.sh`, `scripts/package-macos.sh arm64` / `amd64`, `scripts/package-windows.ps1`. macOS-пакет собирается на macOS, MSI — на Windows. Секреты подписи не заложены в репозиторий. Полный комплект публикуется в `installers/current` только после прохождения всех сборок, через Git LFS.

UI не содержит логотипов/герба Роскомнадзора или Ростелекома и не заявляет официальную связь. Визуальные ориентиры: строгая сине-белая основа, фиолетовые и оранжевые акценты, крупная типографика, русский язык, светлая/тёмная тема и адаптация к телефону.

Правила оформления, адаптация и проверка интерфейса: [вёрстка клиентов](client-design.md).

## Источники трафика и предложения 0.2

TUN сохраняет исходный TCP/UDP tuple и запрашивает владельца у ОС до открытия исходящего соединения. В клиенте хранится ограниченный каталог локальных приложений и наблюдений. Ошибки учитываются отдельно для пары адрес/приложение; ответ одного приложения не скрывает неисправность другого. Только повторная ошибка публикуется через `/api/discover` как `failed_targets`; восстановление — как `resolved_targets`. Сервер хранит подтверждения отдельно по устройствам и возвращает `direct_failed` только для текущего устройства. Устаревшие `targets` от клиентов 0.1 принимаются, но сами по себе не создают предложения в 0.2.

Разрешения адресов используют исходный VLESS credential устройства. `/api/app-vpn` включает отдельный credential того же устройства для локально доверенных приложений; он не расширяет allowlist адресного credential. Отзыв/истечение устройства или блокировка аккаунта исключает оба credential из Xray. Оба маршрута сохраняют проверку публичного IP назначения и запрет служебных сетей на сервере. Сервер аутентифицирует устройство, а принадлежность процесса и решение о доверии проверяются локально; название приложения не является доказательством доверия.

На macOS агент запускает helper до сброса UID. Helper принимает только валидные TCP/UDP tuple через унаследованные анонимные pipes, не имеет публичного API и завершается при закрытии pipes. Он не меняет сеть, не запускает команды и не читает произвольные пути по запросу клиента.


## Ключи, профиль и ручной режим

- Аккаунт хранит `access_key_hash`; публичные `Account`/`Profile` не раскрывают хэш. `Profile.login` и локальный `State.login` передают отображаемое имя. Сервер выдаёт ключ один раз при регистрации/замене; UI очищает значение после подтверждения сохранения.
- `State.BootstrapKey` создаётся один раз при старте нового/обновлённого сервера. Полный профиль экспортируется через админку. Регистрация, вход и привязка проверяют заголовок `X-LineVPN-Profile` в одной транзакции с созданием аккаунта/устройства, чтобы гонка с отзывом не выдала доступ по старому секрету.
- `POST /api/access-key/rotate` позволяет активному устройству заменить ключ своего аккаунта. Администратор делает это через `/api/admin/access-key`. Транзакция отзывает устройства и коды, затем пересобирает разрешения Xray.
- `POST /local/vpn` принимает `enabled: boolean`; выключение требует `confirm: true`. `Config.Disabled` сохраняет намерение до смены сети. Переключение закрывает активные TCP/UDP-потоки и Xray, а `routeEpoch` отклоняет запоздалые подключения. Desktop ожидает новую сетевую сессию; Android при lockdown сохраняет TUN и переводит все потоки в direct, иначе закрывает интерфейс. Ошибки видны в `power_error`. `fail_closed`, `protection_blocked` и `partial_outage` описывают режим и недоступность. Прямого резерва нет.

## Доступность сети

Сетевой сбой сохраняет правила и блокирует защищённые подключения. `vpnFailures` — ограниченный диагностический кэш, не источник разрешений. Повтор идёт только через VPN. Постоянные PF/WFP-правила сохраняются при падении worker и обновлении; startup вызывает recovery только при сохранённом `vpn_disabled: true`. macOS использует временную DNS-запись через scutil и worker под `_linevpn`. Android удерживает дополнительный TUN-дескриптор; защита при смерти процесса требует lockdown. [Границы защиты](security.md).

### Одновременные устройства и UDP

`Runtime.Apply` не перезапускает неизменившуюся конфигурацию. Добавление устройств и app-credentials без удаления прежних правил/ключей обновляет работающий Xray через UserManager и Router. Отзыв, ротация и сужение политики по-прежнему отменяют экземпляр вместе с принятыми потоками. UDP NAT использует `NATMappingAddressAndPortDependent`: несколько адресов или портов назначения одного сокета получают отдельные upstream, атрибуцию и правила. `partial_outage` отличает ошибки отдельных соединений от общей недоступности VPN; ни один сбой не разрешает direct. [Результаты проверки и ограничения](concurrent-devices-media-2026-11-17.md).

## Сохранение правил после переустановки

`Profile.application_rules` возвращает решения аккаунта только для платформы аутентифицированного устройства. Сервер хранит `{id, platform, decision}` в `store.Account.ApplicationRules`; имена, пути и история трафика не передаются. `POST /api/application-rules` принимает до 64 отдельных изменений, максимум 512 идентификаторов на платформу. Запись проверяет действующий токен в транзакции, увеличивает ревизию при изменениях, не перезапускает транспорт и не заменяет список целиком. `only_if_absent` используется при миграции старого локального каталога, чтобы не затереть более новое решение аккаунта. Обычные несинхронизированные пользовательские изменения применяются при доставке; для одного идентификатора действует последнее принятое сервером решение.

Клиент сохраняет `sync_pending` / `sync_confirmed` в `applications.json`. Подтверждённая копия принимает изменения аккаунта; явное несинхронизированное решение остаётся локально до подтверждения записи. Правило из аккаунта применяется только к идентификатору, который ОС уже определила на устройстве. Пустой массив `application_rules` означает поддержку API, отсутствующее поле / null — старый сервер; локальное решение при этом не теряется и не выдаётся за сохранённое в аккаунте.

`Config.Pinned` — очередь ещё не подтверждённых разрешений адресов. Успешный GET убирает уже сохранённые правила, остальные повторно отправляются с актуальной ревизией (до 32 за проход). Ответ, потерянный после серверной записи, не вызывает повторного добавления подтверждённого правила. При выключенном VPN фоновая синхронизация выполняется только пока есть несохранённые решения и не запускает транспорт. `policy_sync_pending` и `policy_sync_error` дают интерфейсу состояние сохранения до переустановки.
