# Развёртывание сервера

Требуется чистый VPS Debian 12/13 или Ubuntu 24.04/26.04, Linux amd64, публичный IPv4/IPv6 и SSH. Домен и покупной сертификат не нужны. Порты: TCP 443 для REALITY, TCP 8443 для TLS API и админки, ваш SSH-порт. На хосте не должны работать другие сервисы на 443/8443.

## GitHub Actions

В **Settings → Secrets and variables → Actions → Repository secrets** добавьте:

| Секрет | Значение |
|---|---|
| `VPS_HOST` | Публичный IP сервера, без `ssh`, имени пользователя и порта |
| `VPS_USERNAME` | SSH-пользователь, например `root` |
| `VPS_PASSWORD` | Пароль SSH-пользователя |

Необязательные секреты: `VPS_PORT` (по умолчанию 22), `VPN_ADMIN_PASSWORD` (16–72 байта, без пробелов по краям), `VPS_KNOWN_HOSTS` (проверенная запись OpenSSH known_hosts). Если пользователь не root, нужен доступ sudo с тем же паролем либо без пароля.

Откройте **Actions → Deploy VPN server → Run workflow**, выберите `main`. Workflow также запускается при изменениях серверного кода или файлов деплоя в `main`. В pull request выполняется только проверка конфигурации; доступа к VPS нет. Изменение секрета само по себе не запускает workflow: после добавления секретов нажмите **Re-run all jobs** у остановившегося запуска или **Run workflow**.

Сначала проверяются секреты; при отсутствии обязательных значений запуск завершается с их названиями до сборки и подключения. Затем GitHub runner запускает тесты серверной части, собирает Linux-бинарники, применяет Ansible и проверяет `/healthz` через HTTPS с полученным по SSH сертификатом, а также доступность TCP 443. Компилятор на VPS не устанавливается. Одновременные деплои в `main` выполняются по очереди.

Пароли читаются из окружения runner, не передаются в аргументах shell и не записываются в репозиторий. При отсутствии `VPN_ADMIN_PASSWORD` Ansible создаёт случайный пароль админки один раз в `/etc/linevpn/admin-password` с правами 0600 и сохраняет его при обновлениях. Узнать его можно по SSH: `sudo cat /etc/linevpn/admin-password`. Если секрет `VPN_ADMIN_PASSWORD` задан, он становится паролем админки при каждом деплое.

Без `VPS_KNOWN_HOSTS` используется первое доверие SSH (`accept-new`) внутри запуска. Для проверки заранее известного ключа добавьте проверенную запись в этот секрет; тогда включается `StrictHostKeyChecking=yes`. Один `ssh-keyscan` без независимой проверки не подтверждает подлинность ключа.

После успешного деплоя профиль подключения доступен в админке: **«Профиль сервера» → «Скопировать профиль»** или **«Скачать .txt»**. Артефакт **vpn-client-bootstrap** содержит только диагностическую ссылку с адресом/отпечатком и публичный сертификат API. Ключ подключения `access` в него намеренно не включается; действующий профиль выдаёт админка. Паролей и закрытых ключей в артефакте нет. Проверки workflow подтверждают установку и доступность сервера; полный туннель на устройствах проверяется по [приёмке](acceptance.md).

## Ручной деплой: четыре значения

Скачайте и распакуйте репозиторий целиком. Запустите `deploy.bat` на Windows или `bash deploy.sh` на Linux/macOS. Скрипт запросит ровно четыре значения:

```text
host: публичный IP VPS
username: SSH-пользователь
password: SSH-пароль
vpn admin password: пароль админки VPN
```

Пароли вводятся скрыто. Пароль админки обязателен: **16–72 UTF-8 байта**, без пробелов по краям. SSH-порт — **22**, отдельного вопроса о порте нет. Для нестандартного порта можно заранее задать необязательную переменную `VPS_PORT`.

На компьютере не нужно устанавливать Go, Python, Ansible или WSL. Windows использует встроенный PowerShell 5.1+ и автоматически устанавливает закреплённый модуль [Posh-SSH 4.0.0](https://www.powershellgallery.com/packages/Posh-SSH/4.0.0) для текущего пользователя. Linux/macOS используют Bash, системные tar/base64 и OpenSSH 8.4+. Администратор Windows для запуска не требуется.

На VPS нужен `root` либо пользователь с sudo: используется **тот же SSH-пароль**, также подходит sudo без пароля. Отдельный пароль sudo скрипт не спрашивает. Поддерживаются Debian 12/13 и Ubuntu 24.04/26.04, amd64. Доступны должны быть SSH и входящие TCP 443/8443 в firewall провайдера; сами 443/8443 должны быть свободны при первой установке.

### Что происходит автоматически

1. Скрипт собирает архив серверных исходников из текущей копии репозитория по `deploy/source-files.txt` и передаёт его по SSH/SFTP. `.git`, GitHub-токены, локальный inventory, Vault и сгенерированные ключи в архив не включаются. Репозиторий приватный, поэтому скачивать его с VPS и вводить GitHub-токен не требуется.
2. На VPS устанавливаются Python и средства сборки. Go 1.27.4 скачивается с `go.dev`, SHA-256 проверяется по официальному индексу. Go и окружение Ansible сохраняются отдельно в `/opt/linevpn-tools`; системный Go не заменяется. Для Debian 12 с Python 3.11 используется ansible-core 2.19.15, для Python 3.12+ — 2.21.6.
3. Выполняются тесты серверных пакетов и сборка. Первый запуск может занять несколько минут; VPS нужен выход к репозиториям ОС, `go.dev`, Go-модулям, PyPI и Ansible Galaxy.
4. Существующий Ansible playbook применяется локально на VPS: создаёт конфигурацию и ключи, устанавливает пароль админки, включает UFW для SSH/443/8443, systemd-службу и таймер обновления сертификата. При обновлении служба может кратковременно перезапуститься.
5. На VPS проверяются HTTPS `/healthz` с его сертификатом и TCP 443. С компьютера проверяется внешняя доступность TCP 443 и 8443. Только после этих проверок показывается успешное завершение.

Первое подключение использует доверие при первом использовании (TOFU): новый SSH-ключ сохраняется автоматически, изменившийся известный ключ отклоняется. Пароли не попадают в аргументы команд или логи. Для передачи sudo-пароля и настроек используется временный файл внутри удалённого каталога с правами 0700, сам файл — 0600; после чтения он удаляется, временные исходники очищаются при завершении. На Windows пароли не записываются в локальный временный файл. При обрыве во время установки исправьте причину и запустите скрипт повторно; автоматического отката нет.

### Ввод из окружения

Те же четыре значения можно передать переменными процесса:

| Переменная | Значение |
|---|---|
| `VPS_HOST` | Публичный IPv4/IPv6 сервера |
| `VPS_USERNAME` | SSH-пользователь |
| `VPS_PASSWORD` | SSH-пароль, также используемый для sudo |
| `VPN_ADMIN_PASSWORD` | Пароль админки VPN |

Если переменная задана, соответствующий вопрос пропускается. Пароли через позиционные аргументы не поддерживаются, чтобы они не оказывались в списке процессов. Секреты GitHub локальный запуск автоматически не читает. Для BAT из другого скрипта без завершающей паузы задайте `LINEVPN_NO_PAUSE=1`.

### Результат и обновления

В конце будут адрес `https://IP:8443/` и публичные данные API (без ключа подключения). Диагностическая ссылка и сертификат также сохраняются в `deploy/ansible/generated/vpn1-bootstrap.txt` и `vpn1-api-cert.pem`. Настройте доверие браузера к полученному сертификату, войдите с введённым паролем админки, получите **«Профиль сервера»**, зарегистрируйтесь в клиенте и одобрите заявку. Проверки установки не заменяют проверку туннеля на устройстве.

Для обновления скачайте свежую версию репозитория (или `git pull --ff-only`) и повторите запуск с теми же четырьмя значениями. Существующие ключи и база сохраняются; введённый пароль админки применяется заново. При смене IP скрипт остановится: изменение конфигурации и сертификата требует отдельного действия. Файлы `vpn1-*` соответствуют последнему успешно полученному результату; при нескольких VPS сохраняйте профили отдельно.

## Пошаговая установка через Ansible

На управляющей машине установите Go 1.27.4 и Python 3.12+, клонируйте репозиторий и выполните:

```bash
scripts/build-server.sh
python3 -m pip install -r deploy/requirements.txt
cd deploy/ansible
cp inventory.example.ini inventory.ini
cp group_vars/vpn.example.yml group_vars/vpn.yml
ansible-galaxy collection install -r requirements.yml
ansible-vault create group_vars/vault.yml
```

В `inventory.ini` укажите VPS и `ansible_port`, если SSH работает не на 22. Firewall использует этот порт, если `vpn_ssh_port` не переопределён. В зашифрованном `group_vars/vault.yml` сохраните:

```yaml
vault_admin_password: "ВАШ_УНИКАЛЬНЫЙ_ПАРОЛЬ_16_72_БАЙТА"
```

Передайте vault-файл явно, потому что он не является группой inventory:

```bash
ansible-playbook deploy.yml --extra-vars @group_vars/vault.yml --ask-vault-pass
```

Playbook создаёт пользователя `linevpn`, ключи REALITY, сертификат TLS с IP в SAN, systemd-службу, месячное обновление сертификата и firewall. Ключи создаются только один раз. Повторный запуск не меняет закреплённый публичный ключ API. Секреты и сгенерированные профили исключены из Git.

После установки в `deploy/ansible/generated/` появятся диагностическая ссылка `linevpn://IP:8443?pin=…` и сертификат API, полученные по проверенному SSH-соединению. Ссылка не содержит ключа подключения и не импортируется новым клиентом. Получите полный профиль `linevpn://IP:8443?pin=…&access=…` в админке; не публикуйте его в логах CI.

## Админка

Адрес: `https://IP:8443/`. Пароль задаётся через `vault_admin_password` / секрет `VPN_ADMIN_PASSWORD` либо создаётся автоматически; на VPS он находится в `/etc/linevpn/admin-password` с режимом 0600. Внесите полученный по SSH сертификат в доверенные сертификаты своего браузера/ОС. Не подтверждайте неизвестный сертификат без проверки. Клиент проверяет SPKI-отпечаток автоматически и отклоняет подмену, просроченный сертификат и HTTP-переадресацию.

Регистрация создаёт `pending`. До одобрения не выдаются рабочие данные устройства. Администратор может одобрить/отклонить заявку, заблокировать аккаунт и отозвать отдельное устройство. Блокировка/отзыв перестраивает Xray и завершает существующие сессии.

### Профиль сервера

После входа откройте раздел **«Профиль сервера»** в меню. Админка получает текущую ссылку подключения; её можно скопировать или скачать файлом `linevpn-server.txt`. Кнопка **«Обновить профиль»** повторно формирует ссылку из адреса API в конфигурации и отпечатка действующего сертификата. Она не меняет ключи или сертификат и не прерывает VPN-сессии.

`GET /api/admin/bootstrap` требует действующей сессии администратора и возвращает только поле `profile`. Для адреса используются настройки сервера, а не HTTP Host; поддерживаются IPv4 и IPv6. При недоступном, просроченном или не соответствующем адресу сертификате профиль не выдаётся. Профиль содержит также ключ подключения `access`, но не предоставляет доступ к аккаунтам: личный ключ пользователя и одобрение остаются обязательными.

## Обслуживание

```bash
sudo systemctl status linevpn
sudo journalctl -u linevpn -n 50
sudo systemctl status linevpn-renew.timer
```

Резервируйте `/etc/linevpn` и `/var/lib/linevpn` в зашифрованном виде. Для согласованной копии BoltDB остановите службу или используйте snapshot-транзакцию. Потеря ключа API требует нового профиля на устройствах. При смене IP требуется обновить конфигурацию и сертификат; playbook не заменяет их молча.

Сборки сервера также сохраняются как артефакт workflow `server-binaries`. Проверка `-check` проверяет поля конфигурации; полный запуск проверяет совместимость Xray и доступность слушателей.



## Перевыпуск профиля и переход на ключи

В админке откройте «Профиль сервера» → **«Перевыпустить профиль»**. Подтверждение объясняет последствия. Старая ссылка перестаёт работать для регистрации, нового входа и привязки по коду; ранее выпущенные коды привязки тоже отзываются. Подключённые устройства продолжают работу. Если нужно отозвать их сеансы и VLESS-доступ, включите **«Также отозвать все подключённые устройства»** перед подтверждением. Тогда каждому устройству понадобятся новый профиль и повторный вход по личному ключу.

«Получить текущий профиль», копирование и скачивание ничего не перевыпускают. Ключ профиля сохраняется в `/var/lib/linevpn/server.db`; повторный деплой и перезапуск службы его не меняют. Восстановление старой резервной БД может вернуть отозванные ключи/сеансы: после восстановления скомпрометированной копии перевыпустите профиль с отзывом устройств и соответствующие ключи пользователей.

После обновления старые пользовательские пароли больше не работают. Для каждого старого аккаунта откройте «Все аккаунты» → «Выдать новый ключ», сохраните результат и безопасно передайте владельцу. Сохраняются ID, имя, статус и правила. Клиенты должны быть пересобраны/обновлены из этой ветки; старые пакеты из `installers/current/` не получают новый интерфейс автоматически. Админка продолжает использовать пароль из `admin-password`.

`POST /api/admin/bootstrap/rotate` принимает `{"confirm":true,"revoke_devices":false}`. `POST /api/admin/access-key` принимает `{"id":"ACCOUNT_ID","confirm":true}`. Оба требуют токен администратора. Если ошибка возникла после сохранения отзыва, операция не откатывается: проверьте состояние службы, получите текущий профиль или снова выпустите ключ. Приватный TLS-ключ или REALITY-ключ при этих действиях не меняются; при их компрометации восстановите сервер из доверенного состояния и отдельно замените криптографические материалы.
