# Развёртывание сервера

Требуется чистый VPS Debian 12/13 или Ubuntu 24.04/26.04, Linux amd64, публичный IPv4/IPv6 и SSH. Домен и покупной сертификат не нужны. Порты: TCP 443 для REALITY, TCP 8443 для клиентского TLS API и публичной HTTPS-админки, ваш SSH-порт. Админка доступна по `https://VPS_IP:8443/` с паролем администратора. На хосте не должны работать другие сервисы на 443/8443.

## GitHub Actions

В **Settings → Secrets and variables → Actions → Repository secrets** добавьте:

| Секрет | Значение |
|---|---|
| `VPS_HOST` | Публичный IP сервера, без `ssh`, имени пользователя и порта |
| `VPS_USERNAME` | SSH-пользователь, например `root` |
| `VPS_PASSWORD` | Пароль SSH-пользователя |

Необязательные секреты: `VPS_PORT` (по умолчанию 22), `VPN_ADMIN_PASSWORD` (16–72 байта, без пробелов по краям), `VPS_KNOWN_HOSTS` (проверенная запись OpenSSH known_hosts). Если пользователь не root, нужен доступ sudo с тем же паролем либо без пароля.

Откройте **Actions → Deploy VPN server → Run workflow**, выберите `main`. Workflow также запускается при изменениях серверного кода или файлов деплоя в `main`. В pull request выполняется только проверка конфигурации; доступа к VPS нет. Изменение секрета само по себе не запускает workflow: после добавления секретов нажмите **Re-run all jobs** у остановившегося запуска или **Run workflow**.

Сначала проверяются секреты; при отсутствии обязательных значений запуск завершается с их названиями до сборки и подключения. Затем GitHub runner запускает тесты серверной части, собирает Linux-бинарники, применяет Ansible и проверяет `/healthz` через HTTPS с полученным по SSH сертификатом, отсутствие административных маршрутов на публичном API и TLS-рукопожатие REALITY на 443 с проверкой сертификата его целевого сайта. Компилятор на VPS не устанавливается. Одновременные деплои в `main` выполняются по очереди.

Пароли читаются из окружения runner, не передаются в аргументах shell и не записываются в репозиторий. При первой установке `VPN_ADMIN_PASSWORD` обязателен. На сервер записывается только bcrypt-хеш, `root:linevpn`, режим 0640. При обновлении без нового пароля сохраняется прежний; старый файл с открытым паролем автоматически заменяется хешем. Из хеша нельзя восстановить пароль. Если секрет задан, он становится паролем админки при деплое.

Без `VPS_KNOWN_HOSTS` используется первое доверие SSH (`accept-new`) внутри запуска. Для проверки заранее известного ключа добавьте проверенную запись в этот секрет; тогда включается `StrictHostKeyChecking=yes`. Один `ssh-keyscan` без независимой проверки не подтверждает подлинность ключа.

После успешного деплоя профиль подключения доступен в админке: **«Профиль сервера» → «Скопировать профиль»** или **«Скачать .txt»**. Артефакт **vpn-client-bootstrap** содержит только диагностическую ссылку с адресом/отпечатком и публичный сертификат API. Ключ подключения `access` в него намеренно не включается; действующий профиль выдаёт админка. Паролей и закрытых ключей в артефакте нет. Проверки workflow подтверждают установку и доступность сервера; полный туннель на устройствах проверяется по [приёмке](acceptance.md).

## Ручной деплой: четыре значения

Скачайте и распакуйте репозиторий целиком. Запустите `deploy.bat` на Windows или `bash deploy.sh` на Linux/macOS. Скрипт запросит ровно четыре значения:

```text
host: публичный IP VPS
username: SSH-пользователь
password: SSH-пароль
vpn admin password: пароль админки VPN
```

Пароли вводятся скрыто. Пароль админки обязателен: **16–72 UTF-8 байта**, без пробелов по краям. SSH-порт — **22**, отдельного вопроса о порте нет. Для нестандартного порта можно заранее задать необязательную переменную `VPS_PORT`.

Сервер собирается на компьютере оператора или в CI: нужен **Go 1.27.4**. Готовый артефакт `vpn-server-bundle` из Actions позволяет обойти локальную сборку: на Linux/macOS задайте `LINEVPN_SERVER_BUNDLE=/путь/linevpn-server-bundle.tar.gz`; на Windows распакуйте его и задайте `LINEVPN_SERVER_BUILD_DIR` на каталог `build` с двумя бинарниками и `SHA256SUMS`. Используйте только комплект из доверенной сборки: контрольная сумма внутри архива не заменяет проверку его источника. Ansible и WSL на компьютере не нужны. Windows использует встроенный PowerShell 5.1+ и автоматически устанавливает закреплённый модуль [Posh-SSH 4.0.0](https://www.powershellgallery.com/packages/Posh-SSH/4.0.0) для текущего пользователя. Linux/macOS используют Bash, Python 3.11+, системные tar/base64 и OpenSSH 8.4+. Администратор Windows для запуска не требуется.

На VPS нужен `root` либо пользователь с sudo: используется **тот же SSH-пароль**, также подходит sudo без пароля. Отдельный пароль sudo скрипт не спрашивает. Поддерживаются Debian 12/13 и Ubuntu 24.04/26.04, amd64. Доступны должны быть SSH и входящие TCP 443/8443 в firewall провайдера; сами 443/8443 должны быть свободны при первой установке.

### Что происходит автоматически

1. На компьютере или runner собираются два Linux amd64 бинарника. `scripts/package-server.sh` создаёт комплект с SHA-256, playbook и необходимыми исходниками. Архив проверяется после передачи, бинарники — ещё раз перед установкой. `.git`, Vault, inventory и локальные секреты не передаются.
2. Передача использует защищённый каталог `/dev/shm`; отсутствие RAM-каталога завершает установку ошибкой. Файл с паролями удаляется до `sudo` и `apt`. Пароль sudo используется только для `sudo -v`; последующие команды получают пустой stdin, а Python — отдельный поток с настройками без SSH-пароля.
3. Root распаковывает комплект в собственный временный каталог. На VPS устанавливаются Python и Ansible, но не Go; тесты и компиляция на VPS не запускаются. Для Python 3.11 используется ansible-core 2.19.15, для Python 3.12+ — 2.21.6. Все Python-пакеты закреплены версиями и хешами wheels; коллекция Ansible — точной версией. Существующие каталоги инструментов проверяются по владельцу и правам. Нужен выход к репозиториям ОС, PyPI и Ansible Galaxy.
4. Ansible устанавливает бинарники, bcrypt-хеш администратора, root-owned конфигурацию и ключи, UFW для SSH/443/8443, службу и таймер обновления сертификата. Сервис пишет только в `/var/lib/linevpn`. Повторный деплой может перезапустить VPN и оборвать активные соединения.
5. Проверяются HTTPS API, публичная страница входа, запрет доступа к данным и действиям админки без сессии и TLS целевого REALITY-сайта. Linux/macOS повторяет проверку с компьютера; Windows дополнительно проверяет доступность портов извне. Это ещё не проверка авторизованного VLESS-трафика.

По умолчанию действует TOFU (`accept-new`): новый SSH-ключ принимается, изменившийся известный ключ отклоняется. Для Linux/macOS задайте **`VPS_HOST_FINGERPRINT=SHA256:…`**, полученный через независимый доверенный канал, например консоль провайдера. В этом режиме доверяется только совпавший ключ, а не все ответы `ssh-keyscan`. `VPS_IDENTITY_FILE` выбирает SSH-ключ; пустое явно заданное `VPS_PASSWORD` подходит для ключа и `NOPASSWD`. При входе ключом с парольным sudo задайте пароль sudo в `VPS_PASSWORD`. Windows-лаунчер пока использует парольный SSH и TOFU.

Linux/macOS передаёт askpass пароль через локальный файл 0600, а не окружение `ssh`. Локальная и удалённая очистка выполняются при обычном завершении и сигналах; SSH-очистка ограничена 30 секундами. Удалённый файл input не остаётся на диске после аварии во время `apt`; tmpfs может попасть в swap, поэтому для защиты от дисковых снимков RAM-временных данных используйте отключённый или зашифрованный swap. После ошибки устраните причину и повторите деплой.

### Ввод из окружения

Те же четыре значения можно передать переменными процесса:

| Переменная | Значение |
|---|---|
| `VPS_HOST` | Публичный IPv4/IPv6 сервера |
| `VPS_USERNAME` | SSH-пользователь |
| `VPS_PASSWORD` | SSH-пароль, также используемый для sudo |
| `VPN_ADMIN_PASSWORD` | Пароль админки VPN |

Если переменная задана, соответствующий вопрос пропускается. Пароли через позиционные аргументы не поддерживаются, чтобы они не оказывались в списке процессов. Секреты GitHub локальный запуск автоматически не читает. Для BAT из другого скрипта без завершающей паузы задайте `LINEVPN_NO_PAUSE=1`.

### Результат и обновления

В конце будут публичный адрес админки `https://VPS_IP:8443/` и публичные данные API (без ключа подключения). Диагностическая ссылка и сертификат также сохраняются в `deploy/ansible/generated/vpn1-bootstrap.txt` и `vpn1-api-cert.pem`. Настройте доверие браузера к полученному сертификату, войдите с введённым паролем админки, получите **«Профиль сервера»**, зарегистрируйтесь в клиенте и одобрите заявку. Проверки установки не заменяют проверку туннеля на устройстве.

Для обновления скачайте свежую версию репозитория (или `git pull --ff-only`) и повторите запуск с теми же четырьмя значениями. Существующие ключи и база сохраняются; введённый пароль админки применяется заново. При смене IP скрипт остановится: изменение конфигурации и сертификата требует отдельного действия. Файлы `vpn1-*` соответствуют последнему успешно полученному результату; при нескольких VPS сохраняйте профили отдельно.

## Пошаговая установка через Ansible

На управляющей машине установите Go 1.27.4 и Python 3.12+, клонируйте репозиторий и выполните:

```bash
scripts/build-server.sh
python3 -m pip install -r deploy/requirements.txt
cd deploy/ansible
cp inventory.example.ini inventory.ini
cp group_vars/vpn.example.yml group_vars/vpn.yml
ansible-galaxy collection install -r requirements.yml
ansible-vault create group_vars/vault.yml
```

В `inventory.ini` укажите VPS и `ansible_port`, если SSH работает не на 22. Firewall использует этот порт, если `vpn_ssh_port` не переопределён. В зашифрованном `group_vars/vault.yml` сохраните:

```yaml
vault_admin_password: "ВАШ_УНИКАЛЬНЫЙ_ПАРОЛЬ_16_72_БАЙТА"
```

Передайте vault-файл явно, потому что он не является группой inventory:

```bash
ansible-playbook deploy.yml --extra-vars @group_vars/vault.yml --ask-vault-pass
```

Playbook создаёт пользователя `linevpn`, ключи REALITY, сертификат TLS с IP в SAN, systemd-службу, месячное обновление сертификата и firewall. Ключи создаются только один раз. Повторный запуск не меняет закреплённый публичный ключ API. Секреты и сгенерированные профили исключены из Git.

После установки в `deploy/ansible/generated/` появятся диагностическая ссылка `linevpn://IP:8443?pin=…` и сертификат API, полученные по проверенному SSH-соединению. Ссылка не содержит ключа подключения и не импортируется новым клиентом. Получите полный профиль `linevpn://IP:8443?pin=…&access=…` в админке; не публикуйте его в логах CI.

## Админка

Откройте **`https://VPS_IP:8443/`** в браузере и введите пароль администратора.
Для IPv6 используйте квадратные скобки: `https://[VPS_IPV6]:8443/`.
SSH-туннель для входа не требуется. TCP 443 занят VPN-транспортом, поэтому порт
`8443` в адресе обязателен.

Штатный деплой выставляет `public_admin: true` в существующем `server.json`,
сохраняя остальные параметры и ключи. Без этого флага сервер сохраняет прежний
режим: публично работает только клиентский API. Отдельный listener
`admin_address` остаётся на `127.0.0.1:8444` для локального доступа; открывать его
в firewall не нужно. Страница входа и её ресурсы общедоступны, данные аккаунтов,
профиль сервера и все административные действия требуют действующего
bearer-токена администратора. Ограничение входа — 8 попыток с IP (IPv6 /64) и
30 суммарно за 15 минут; заголовок `X-Forwarded-For` не меняет источник запроса.
Запросы с чужим `Origin` отклоняются.

Свежий и продлённый сертификат содержит публичный IP и loopback SAN; обновление
старого сертификата сохраняет его ключ и клиентский pin.

Пароль задаётся через `vault_admin_password` / `VPN_ADMIN_PASSWORD`; файл `/etc/linevpn/admin-password` содержит только bcrypt-хеш. Конфигурация и TLS/REALITY-ключи принадлежат root, доступны сервисной группе только для чтения. Внесите полученный по SSH сертификат в доверенные сертификаты своего браузера/ОС. Не подтверждайте неизвестный сертификат без проверки. Клиент проверяет SPKI-отпечаток автоматически и отклоняет подмену, просроченный сертификат и HTTP-переадресацию.

Регистрация создаёт `pending`. До одобрения не выдаются рабочие данные устройства. Администратор может одобрить/отклонить заявку, заблокировать аккаунт и отозвать отдельное устройство. Блокировка/отзыв перестраивает Xray и завершает существующие сессии.

### Профиль сервера

После входа откройте раздел **«Профиль сервера»** в меню. Админка получает текущую ссылку подключения; её можно скопировать или скачать файлом `linevpn-server.txt`. Кнопка **«Обновить профиль»** повторно формирует ссылку из адреса API в конфигурации и отпечатка действующего сертификата. Она не меняет ключи или сертификат и не прерывает VPN-сессии.

`GET /api/admin/bootstrap` требует действующей сессии администратора и возвращает только поле `profile`. Для адреса используются настройки сервера, а не HTTP Host; поддерживаются IPv4 и IPv6. При недоступном, просроченном или не соответствующем адресу сертификате профиль не выдаётся. Профиль содержит также ключ подключения `access`, но не предоставляет доступ к аккаунтам: личный ключ пользователя и одобрение остаются обязательными. Профиль — секрет: передавайте его лично, не публикуйте в общих чатах или отчётах.

## Обслуживание

```bash
sudo systemctl status linevpn
sudo journalctl -u linevpn -n 50
sudo systemctl status linevpn-renew.timer
```

Резервируйте `/etc/linevpn` и `/var/lib/linevpn` в зашифрованном виде. Для согласованной копии BoltDB остановите службу или используйте snapshot-транзакцию. Потеря ключа API требует нового профиля на устройствах. При смене IP требуется обновить конфигурацию и сертификат; playbook не заменяет их молча.

Таймер ежемесячно продлевает сертификат с **тем же ключом**; новый сертификат подхватывается на следующем TLS-рукопожатии без перезапуска VPN. При сбое таймера выполните `sudo systemctl start linevpn-renew.service` и проверьте его журнал. Проверка срока на клиентах сохранена; ошибки различают истечение сертификата и неверные часы.

Комплект ручного деплоя сохраняется как `vpn-server-bundle`, отдельные бинарники — как `server-binaries` сборочного workflow. `-check` проверяет конфигурацию и пару сертификат/ключ без открытия БД; Ansible запускает его от пользователя `linevpn`. Полный запуск проверяет Xray и слушатели.



## Перевыпуск профиля и переход на ключи

В админке откройте «Профиль сервера» → **«Перевыпустить профиль»**. Подтверждение объясняет последствия. Старая ссылка перестаёт работать для регистрации, нового входа и привязки по коду; ранее выпущенные коды привязки тоже отзываются. Подключённые устройства продолжают работу. Если нужно отозвать их сеансы и VLESS-доступ, включите **«Также отозвать все подключённые устройства»** и введите **`REVOKE-ALL`** перед подтверждением. Тогда каждому устройству понадобятся новый профиль и повторный вход по личному ключу.

«Получить текущий профиль», копирование и скачивание ничего не перевыпускают. Ключ профиля сохраняется в `/var/lib/linevpn/server.db`; повторный деплой и перезапуск службы его не меняют. Восстановление старой резервной БД может вернуть отозванные ключи/сеансы: после восстановления скомпрометированной копии перевыпустите профиль с отзывом устройств и соответствующие ключи пользователей.

После обновления старые пользовательские пароли больше не работают. Для каждого старого аккаунта откройте «Все аккаунты» → «Выдать новый ключ», сохраните результат и безопасно передайте владельцу. Сохраняются ID, имя, статус и правила. Клиенты должны быть пересобраны/обновлены из этой ветки; старые пакеты из `installers/current/` не получают новый интерфейс автоматически. Пароль администратора сохраняет прежнее значение, но файл `admin-password` после обновления содержит его хеш.

`POST /api/admin/bootstrap/rotate` принимает `{"confirm":true,"revoke_devices":false}`. `POST /api/admin/access-key` принимает `{"id":"ACCOUNT_ID","confirm":true}`. Оба требуют токен администратора. Для массового отзыва добавьте `"revoke_confirmation":"REVOKE-ALL"`. Если Xray не применил уже сохранённый отзыв, он остаётся закрытым, а сервер повторяет применение актуальной БД каждую минуту. Новый ключ/профиль всё равно возвращается вызывающему клиенту; ответ содержит `vpn_apply_pending`. Отката на отозванные секреты нет. Приватный TLS-ключ или REALITY-ключ при этих действиях не меняются; при их компрометации восстановите сервер из доверенного состояния и отдельно замените криптографические материалы.

Для пользовательского `POST /api/access-key/rotate` обязательны `confirm: true` и `current_key` с действующим личным ключом. Одного токена устройства недостаточно. Обновлённый клиент запрашивает ключ в отдельном диалоге и очищает поле после отправки. Старые клиенты должны обновиться для самостоятельной ротации; вход и синхронизация не меняются. Администратор сохраняет возможность восстановления через `/api/admin/access-key`.

## Независимые проверки, деплой и выпуск установщиков

- **Code checks** (`checks.yml`) выполняет проверки Go, скриптов и UI на push/PR.
- **Deploy VPN server** (`deploy.yml`) проверяет серверные изменения и после
  слияния в `main` развёртывает сервер. Изменения клиентской версии и сборка
  APK/MSI/DMG ему не требуются.
- **Build or publish installers** (`build.yml`) запускается вручную через
  Actions → Run workflow. При `publish=false` собирает тестовый комплект текущей
  версии и сохраняет артефакты; установленный каталог не заменяется. Android в
  таком комплекте использует тестовую подпись и не предназначен для обновления
  установленного приложения. При `publish=true` доступен только `main`: номер
  версии должен быть выше опубликованного, используется прежний Android-ключ,
  полный комплект публикуется только после всех проверок. Изменение `main` во
  время сборки останавливает публикацию, чтобы не смешать исходники и бинарники.

Для нового клиентского выпуска согласованно увеличьте версию в
`apps/desktop/package.json` и `apps/desktop/package-lock.json`, влейте её в `main`
и запустите `build.yml` с `publish=true`. Обычная сборка проверяет согласованность
метаданных; запрет повторной публикации проверяется перед выпуском и ещё раз
в `publish-installers.py`.
