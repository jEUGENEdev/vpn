## Причины и исправления

1. Добавление устройства или разрешения вызывало полный перезапуск Xray с отменой активных XHTTP-потоков всех клиентов. Теперь новые пользователи и расширение разрешений применяются к работающему транспорту; неизменённая конфигурация ничего не перезапускает. Отзыв доступа и сужение правил по-прежнему отменяют старые потоки через перезапуск.
2. NAT по умолчанию объединял UDP-пакеты одного исходного сокета к разным назначениям, тогда как клиент обслуживал только первое назначение. Другие медиасерверы теряли пакеты до определения приложения, проверки разрешения и учёта ошибки. Теперь NAT разделяет потоки по IP **и порту** назначения для IPv4/IPv6.
3. Ошибка одного VPN-потока включала прямой резерв для всего клиента. Теперь резерв ограничен сочетанием адреса, порта, TCP/UDP и приложения. Обычный тайм-аут простоя после полученного ответа не означает отказ VPN. Приоритет доступности сети и уведомления о прямом резерве сохраняются.
4. Повторная отправка без ответа в одном прямом UDP-потоке учитывалась лишь однажды. Теперь новые данные в следующем окне наблюдения могут сформировать второе наблюдение и предложение разрешить VPN. Без новых данных ошибок не прибавляется; поздний ответ очищает предложение, соединение не закрывается ради диагностики.

## Проверки

- Реальный локальный Xray / VLESS / XHTTP / REALITY: одновременно два устройства, по TCP- и UDP-потоку на каждое; добавление устройства, включение доверия приложениям, расширение доменных/IP-разрешений и повтор конфигурации не обрывают потоки.
- Существующие проверки запрета неразрешённого трафика и отключения TCP/UDP при удалении устройства сохраняются.
- Реальный sing-tun UDP NAT и клиентский обработчик: один исходный сокет, три назначения, повторные пакеты, IPv4/IPv6, сохранение определения приложения для каждого назначения.
- Одинаковые название и платформа двух устройств не объединяют сессии: отдельные токены и UUID; повторный вход и удаление одного не отзывают второе.
- Проверки изоляции прямого резерва по приложению, адресу, порту и протоколу; простоя UDP; повторных отправок без ответа и позднего восстановления.
- `go test -race -tags with_gvisor ./...` и `go vet -tags with_gvisor ./...`.
- DOM-проверки общего интерфейса, включая отдельное отображение частичного прямого резерва; `node --check internal/ui/client/app.js`.
- Кросс-компиляция общего ядра: Windows amd64, macOS amd64/arm64, Android arm64; сборка Linux-сервера.

В отдельной временной копии возвращены старое объединение UDP и полный перезапуск транспорта: новые регрессионные проверки воспроизводят потерю второго/третьего назначения и перезапуск при добавлении второго устройства. Проверка повторных UDP-отправок также воспроизводит отсутствие предложения на прежнем обработчике.

## Применение и оставшаяся проверка

Нужны **обновление сервера и новые клиентские сборки**: серверная часть исправляет подключение устройств, общая клиентская часть — UDP, диагностику и резерв. Схема БД, личные ключи, профиль сервера и сохранённые разрешения не меняются. Эта правка исходников не обновляет уже установленные приложения и не заменяет опубликованные установщики автоматически.

Локальные проверки не заменяют испытание физических Android/Windows/macOS-устройств. После установки проверить два устройства одного аккаунта одновременно, медиазагрузки и звонки в проблемных приложениях, один и разные внешние IP, IPv4/IPv6. Проверить, что VPN-разрешение для одного адреса не распространяется на отдельные CDN-адреса, а доверенное приложение получает VPN только после подтверждения владельца сокета ОС. Затем отключить VPN и убедиться, что обычная сеть доступна.

Неизвестный владелец сокета, DoH/DoT и встроенные IP остаются ограничениями доменной атрибуции: источник не угадывается по соседнему адресу. См. [границы защиты](security.md).
