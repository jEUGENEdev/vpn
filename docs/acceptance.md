# Приёмка перед использованием

Запускайте на отдельных тестовых устройствах/VM с доступом к локальной консоли. Нельзя считать выпуск готовым по одним unit-тестам или успешной упаковке.

Для каждого сценария проверяйте фактический трафик на физическом интерфейсе. При рабочем VPN одобренные адреса и доверенные приложения должны использовать VPN-сервер. При сбое VPN/API, выключении или остановке службы ожидается прямой доступ с явным сообщением об отсутствии VPN-защиты. На Android отдельно учитывайте системный lockdown: приложение не может снять его самостоятельно.

Android: отдельно проверить отказ в уведомлениях, отзыв VpnService, включённый и выключенный lockdown, выгрузку OEM-энергосбережением. Windows: service recovery, удаление старых WFP-фильтров, DNS Client service, DHCPv4/v6 и существующие firewall. macOS: очистка старого PF anchor, временная DNS-сессия и восстановление старых DNS, dropped UID, загрузка LaunchDaemon, сетевые интерфейсы после сна и другие Network Extensions.

## Автоматизированные проверки CI

**Исторический прогон прежнего режима (не подтверждает текущие изменения):** Windows Server 2025: MSI установился, служба запустила Wintun/WFP; Fake-DNS, direct IP, блокировка после локального одобрения без сервера и WFP после остановки службы пройдены. Android 15 x86_64 emulator: VpnService/TUN, Fake-DNS, direct IP и локальная защита при отсутствии сервера пройдены. macOS 15 Intel и macOS 26 Apple Silicon: PKG, служба/TUN, Fake-DNS, direct, локальная блокировка и сохранение PF после остановки службы пройдены. Это ограниченные smoke-тесты; строки таблицы выше относятся к полным сценариям на целевых устройствах, включая настоящий VPS и проверки пакетов.

## Предложения и приложения 0.2

1. Рабочий прямой TCP/UDP обмен не создаёт предложение; повторная ошибка одного источника создаёт его. Успех снимает только ошибку этого источника. Старые успешные discoveries 0.1 не отображаются.
2. Проверить несколько поддоменов и IP: одна раскрываемая группа на регистрируемый домен, отдельные private-suffix арендаторы и IP. Обновление не меняет порядок, фокус и раскрытие.
3. На Android, Windows и macOS определить владельца реального TUN-подключения. Доверить его, проверить прямой резерв без VPN, вернуть режим адресов. Автоматизированные нативные сценарии выполняют эти проверки на эмуляторе и установленных MSI/PKG.
4. При рабочем сервере доверенное приложение использует отдельный VPN-маршрут; другое приложение к тому же неразрешённому адресу остаётся прямым. Отзыв доверия сохраняет правила доменов; отзыв устройства прекращает оба VPN-маршрута.
5. При неизвестном владельце явно показать ограничение, не угадывать приложение и не переносить доверие на похожее имя/заменённый бинарник. Подтверждение и откладывание окна не вызывают поток повторных окон.

## История источников и поиск

- После сбоя прямого и защищённого запроса проверить точный адрес и источник в «Что происходит», подробностях и системном уведомлении. Сбой с неопределённым владельцем не должен приписываться известному приложению, которое также обращалось к этому адресу.
- После восстановления и исчезновения запроса из очереди источник старого события должен сохраниться. Общий сбой службы не должен изображаться запросом конкретного приложения.
- Найти старое событие, не входящее в последние три, по пути приложения и по IPv6; раскрыть/свернуть историю. Проверить пустую выдачу, очистку поля, сохранение фокуса, раскрытых подробностей и фильтра при обновлениях.
- Проверить поиск в каждом списке, включая источники внутри группы поддоменов, приложения с одинаковым именем и разными путями, устройства и аккаунты администратора. Действие из отфильтрованной строки должно затрагивать только выбранную запись. Поиск сам по себе не меняет доступ или маршрутизацию.
- `scripts/test-ui.cjs` содержит эти сценарии и снимки истории на desktop/mobile. Нативные уведомления и определение владельца в ОС требуют отдельной проверки на целевом устройстве.


## Ключи и переключатель VPN

На реальном VPS и каждой целевой платформе ещё требуется проверить:

1. Регистрация по имени, однократная выдача/копирование ключа, ожидание одобрения и вход только по ключу; отображение того же имени в админке и клиенте.
2. Выдача ключа старому аккаунту сохраняет его правила и ID. Старый пароль не принимается. Замена ключа закрывает реальные VPN-соединения всех устройств и отзывает старые коды.
3. Перевыпуск общего профиля: старый профиль не регистрирует и не подключает устройства, новый работает. Без массового отзыва текущие устройства продолжают работать; с отзывом теряют API и VLESS-доступ.
4. Отмена «Выключить VPN» ничего не меняет. Подтверждение переводит TCP/UDP напрямую, а выбор сохраняется после перезапуска. UI и Android-уведомление явно показывают выключенное состояние.
5. Включение закрывает уже открытые прямые соединения, в том числе запросы, начавшиеся во время переключения. При недоступном сервере защищённый адрес/доверенное приложение блокируется; прямой резерв запрещён. Проверить пакетным захватом IPv4/IPv6, DNS-кэши и Android lockdown.

Go-тесты проверяют серверный отзыв, сохранение идентичности, изоляцию, перезапуск и маршрутизацию на локальных listener. `scripts/test-ui.cjs` содержит сценарии новых форм, однократной выдачи, подтверждения/отмены и переключателя; для запуска нужен доступный Chromium. Эти проверки не заменяют нативную проверку трафика.

## Проверки устройств и установки macOS

- При входе системное имя показано без редактирования; при его отсутствии доступны выбор своего устройства и добавление текущего, включая пустой список. Чужие аккаунты и платформы в выбор не попадают.
- Повторная авторизация сохранённого устройства не создаёт дубликат и инвалидирует оба прежних VPN-ключа и API-токен. Pair-код сохраняется на этапе выбора и расходуется атомарно при завершении.
- Удаление своего/другого устройства и старой отозванной записи удаляет запись и связанные коды. После перезапуска сервера она не появляется; обе старые VPN-учётные записи и API закрыты, активные TCP/UDP-потоки остановлены. Локальные разрешённые адреса сохраняются; при недоступном VPN работает прямой резерв.
- JSON `/api/admin/accounts` не содержит правила, их счётчики или ревизию; интерфейс не отображает пользовательские разрешения.
- На Intel и Apple Silicon проверить **финальный** DMG: `hdiutil verify`, архитектуру, `codesign --verify --deep --strict` приложения, подпись агента из PKG, установку PKG из образа и запуск скопированного GUI. CI сохраняет `macos-signing.txt` и `macos-gui.txt`.
- На чистом Mac скачать DMG через браузер, сохранив quarantine. Для release обязательны `spctl` и stapled tickets приложения/PKG/DMG; preview не проходит обычное доверие Gatekeeper. Проверка на CI без quarantine не заменяет этот сценарий.

## Полное выключение VPN

После установки **новой** сборки на каждой платформе проверьте два цикла включения/выключения. В off должны отсутствовать TUN и собственные сетевые блокировки, работать обычные DNS и прямое соединение, включая ранее одобренный адрес. Остановка и запуск службы в сохранённом off не должны создавать VPN. После включения сохраняются правила и прямой резерв при недоступном сервере; аварийная остановка enabled-службы освобождает сеть.

- macOS/Windows: `scripts/test-desktop-power.py` вызывается из нативных CI-сценариев после проверки прямого резерва одобренного IP. Он проверяет реальные системные DNS, прямой HTTP, остановку/запуск в off и повторное включение. Только на одноразовых CI-машинах.
- Android: `VpnSmokeTest` проверяет удаление VPN-сети и DNS, прямой запрос через обычную сеть, перезапуск off-службы и прямой резерв после включения. Отдельно вручную проверьте отказ выключения с системным lockdown и переход в настройки.
- Unit: ошибки и повтор восстановления DNS, DHCP и статические DNS, новые настройки между циклами, сохранение пользовательских изменений, прямой off-режим при lockdown, переходное состояние и отсутствие фонового sync в off.

Кросс-компиляция и unit-тесты не заменяют эти нативные проверки.

## Блокировка при сбоях

Актуальная матрица: [fail-closed-vpn.md](fail-closed-vpn.md). Проверки ранних сборок с автоматическим прямым резервом не подтверждают новое поведение.

- Все платформы: для TCP/UDP и IPv4/IPv6 отключить API/VPN, отозвать ключ, оборвать чтение/запись и потерять первый ответ. Защищённые потоки не появляются на прямом интерфейсе, повтор идёт через VPN. Несвязанный прямой трафик остаётся доступным при живом перехвате.
- Windows/macOS: убить worker, дождаться перезапуска и сменить сетевой интерфейс; PF/WFP не снимаются. Если TUN отсутствует, допустима блокировка всей сети. Повторить с существующими TCP/UDP-потоками. Обновление сохраняет защиту.
- Ручное выключение: все адреса и приложения идут напрямую, сервер не нужен, режим переживает перезапуск. Отмена подтверждения ничего не меняет; ошибка очистки не показывается как успешный off.
- Android: повторить с lockdown и без него. С lockdown кнопка off оставляет TUN в прямом режиме. После смерти процесса без lockdown гарантий нет; интерфейс сообщает об этой настройке.
- Удаление/recovery: восстановление сети — явное действие; чужие настройки сохраняются.

Нативные проверки новой политики на физических устройствах пока не выполнены.

## Полный режим и согласие приложений

На одноразовых Windows/macOS/Android-хостах после установки новой версии:

1. В selective разрешить домен в приложении A. Из приложения B без решения и из неатрибутируемого процесса проверить TCP/UDP IPv4/IPv6 к этому домену: ни VPN-egress, ни прямого обхода. Разрешить B только адреса, повторить; затем запретить VPN B и проверить закрытие активных потоков.
2. Выбрать «Весь трафик»: проверить выходной IP через IPv4/IPv6, QUIC/UDP, HTTPS и приложения с решением denied; это явное общее разрешение. Проверить DNS A/AAAA/TXT/SRV/HTTPS по TCP/UDP, отсутствие прямых DNS-пакетов на физическом интерфейсе. Серверные private/metadata destinations должны оставаться запрещёнными.
3. Оборвать транспорт/API, отозвать credential, сменить Wi-Fi/мобильную сеть, усыпить/разбудить устройство: пользовательский трафик не должен уходить напрямую. Служебное соединение до VPN/API — необходимое исключение.
4. Переключать all/selective с активными потоками и DNS; старые потоки закрываются. Перезапуск/обновление сохраняют режим и решения. Выключение VPN явно возвращает direct и сохраняет выбранный режим для следующего включения.
5. На Android проверить обычную смерть worker и всего процесса отдельно; для последнего включить always-on + lockdown. На desktop проверить нативные правила PF/WFP. Linux unit-тесты и кросс-сборка эти проверки не заменяют.

## Desktop 0.3.0: управление и название «Сеть»

На одноразовых Windows/macOS хостах проверить:

1. Непривилегированное приложение читает `ui-token`, но POST к прежнему
   `/local/traffic-mode`, `/local/applications`, `/local/vpn` получает 403.
   Защищённый запрос нельзя разрешить через ID или квитанцию без административного
   канала; `control/session.json` недоступен обычному пользователю.
2. При реальном изменении появляется UAC / запрос администратора, затем конкретное
   действие из службы. Отмена любого окна сохраняет политику. Подмена digest,
   истёкший запрос, повтор подтверждения и перезапуск не исполняют команду.
3. Подставной HTTPS-сервер на прежнем порту отклоняется до передачи Authorization
   или тела запроса. UI берётся из пакета; чтение состояния не вызывает elevation.
4. Вход, регистрация, выдача/отзыв разрешения, оба режима и выключение работают
   через подтверждение. После перезапуска службы UI восстанавливает состояние
   без повторного POST. Проверить сетевое поведение по сценариям выше.
5. На чистой установке и после обновления имя — «Сеть», иконка собственная
   в Dock/панели задач, трее, меню приложений, уведомлениях и списке удаления.
   Старый macOS bundle удаляется только после установки нового с тем же bundle ID.
   Чужой bundle по целевому пути должен остановить установку без изменения службы.
   Сохраняются профиль, решения, ui-token, состояние off и подпись обновления.

`scripts/desktop_control_fixture.py` используется только в GitHub Actions на
одноразовых нативных хостах. Он проверяет 403 старого публичного API, затем
использует уже имеющиеся административные права CI для review/commit. Это
проверка транспорта и сетевого состояния, а не проверка окон UAC/AppleScript;
последние требуется пройти интерактивно.

## Переключение Android между VPN-приложениями

На одноразовом устройстве с двумя VPN, без always-on: подключить «Сеть»,
переключиться на другое VPN-приложение, отключить его и вернуться в уже открытое
окно «Сети». Должна появиться кнопка «Открыть VPN», без автоматического захвата
соединения. Повторить запуск с отменой системного запроса, затем с подтверждением.
Проверить появление VPN-сети и системного значка, работу DNS и сохранение правил.
Не удалять профили и данные приложения. Повторить с закрытием и повторным
открытием окна, а также с поворотом экрана во время запроса разрешения.

Отдельно выключить VPN кнопкой внутри «Сети» и включить снова: перед включением
должно проверяться системное разрешение. При отмене не должно быть запроса
на включение к локальному API. Для выключения разрешение VPN не запрашивается.

Назначить другому VPN always-on/lockdown. Отказ Android должен давать понятное
сообщение о системных настройках, без ложного состояния «VPN включён».
После ручного отключения этих опций у другого приложения запуск «Сети» должен
работать без удаления профиля. Приложение не меняет настройки другого VPN само.
Сохранённое явное выключение «Сети» должно переживать повторный запуск службы.

Автотест `VpnSmokeTest` покрывает возвращение уже открытого окна к рабочей
кнопке после остановки службы и повторный запуск без удаления данных.
Реальное переключение владельца VPN и OEM-диалоги требуют указанной ручной
проверки; остановка службы в тесте не доказывает их поведение.
