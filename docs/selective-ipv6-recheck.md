# Повторная проверка IPv6 в выборочном режиме

Изменение основано на `main` `1f852aaf6f3b2e872b6e421fe47a05ac07949dc3`.
Добавлены тесты, этот отчёт и описанное ниже исправление
преждевременного закрытия ответа после отправки. Предыдущая правка HTTPS/SVCB
для полного режима не использовалась: она не объясняет исходное сообщение
из режима «Только разрешённые приложения и адреса».

## Что проверено

`TestSelectiveIPv6RealTunnelAndEgressFailure` соединяет настоящий TCP-обработчик
клиента, выборочный маршрут, VLESS/XHTTP/REALITY, серверное разрешение и реальный
IPv6-сокет назначения на loopback. Идентификация приложения задаётся тестом;
нативный TUN и определение процесса на устройстве пользователя здесь не проверяются.

| Сценарий | Результат |
| --- | --- |
| Приложение «по адресам» + разрешённый IPv6 | TCP round trip проходит |
| Доверенное приложение + IPv6 без адресного правила | TCP round trip проходит |
| Разрешённый IPv6 + отказ IPv6-сокета на выходе сервера | Соединение не получает ответ; появляется `vpn_issues` с IPv6 и приложением |
| Доверенное приложение + тот же отказ на выходе | Такой же результат |
| Приложение «по адресам» + восстановление IPv6-выхода после отказа | Повторное соединение проходит и снимает ошибку этого назначения |
| Доверенное приложение + то же восстановление | Такой же результат без перезапуска клиента или Xray |
| Прямые клиентские соединения во всех шести случаях | Ноль попыток |

Отказ моделируется `ENETUNREACH` до `connect()` для тестового публичного IPv6.
Пакеты на этот IP не отправляются. Исходный анонимизированный адрес пользователя
не использовался как сетевое назначение. Для успешного сценария только в тесте
разрешён `::1`; серверные ограничения production не менялись.
В сценариях восстановления сначала возвращается `ENETUNREACH` для локального
IPv6-назначения, затем разрешается сокет к нему. Клиент, сервер, credentials и
политика остаются прежними; отправку повторяет новый поток того же приложения.

Дополнительно прошли существующие проверки согласия приложения, запрета доступа
неопределённому/неодобренному источнику, восстановления правил из API, эквивалентных
записей IPv6 и отсутствия прямого резерва. Расширенный транспортный тест проверяет
TCP и UDP до настоящих IPv4/IPv6 loopback через оба VLESS credential, а также отзыв.

Проверки: `go test -count=1 -race -tags with_gvisor ./internal/client ./internal/transport`
и `go vet -tags with_gvisor ./internal/client ./internal/transport` — PASS.
Отдельные тесты `internal/policy` и `internal/owner` — PASS.
После добавления двух сценариев восстановления повторно прошли с `-race`
`TestSelectiveIPv6RealTunnelAndEgressFailure`,
`TestVPNFailureIsScopedToEndpointProtocolAndApplication` и
`TestProtectedFailureIsScopedAndCountedOnce`.

## Что следует из результата

В выборочном режиме обычный AAAA-запрос получает Fake-IP, который восстанавливается
в домен до dial. Обычный IPv6 в `vpn_issues` означает, что текущий поток обрабатывался
как буквальный IP. Возможные источники такого IP — собственный DNS/DoH приложения,
его кэш или встроенный адрес; сама строка ошибки не устанавливает источник.

«Только через VPN» — выбранная политика ошибочного потока. Она не содержит причины
серверного отказа. Запись хранится до получения ответа от того же адреса,
приложения, протокола и порта. Ответ другого назначения не снимает старую ошибку,
но сама запись не запрещает повторные соединения и не меняет маршрут.

## Уточнения по VPS и Android

Пользователь подтвердил Android, выборочный режим и доверие всему трафику
приложения. Версия клиента описана как последняя; точный номер APK не подтверждён.
На VPS Timeweb Cloud с Ubuntu 26.04.1 первоначально был только link-local IPv6
на внешнем интерфейсе, маршрут выбирал его как source, а `curl -6` завершался
ошибкой подключения. Это подтверждает неисправность IPv6-выхода в тот момент.

В последующем выводе пользователя появился публичный динамический IPv6,
маршрут выбирал его, а `curl -6` получил HTTP/2 200. Netplan содержит
`dhcp4: true`, `dhcp6: true`, служба `systemd-networkd` включена в автозагрузку.
Отсутствие отдельной `dhcpcd6.service` совместимо с DHCPv6 в networkd.
Получение и продление адреса после следующего запуска VPS отдельно не проверялись.

Успех одного HTTPS-запроса не доказывает доступность каждого IPv6-назначения
или UDP. Пользователь сообщил об оставшихся проблемах на Android; для их
локализации нужны свежие строки с временем, протоколом и портом, а также описание
неработающего действия. Нужно различить новый отказ и сохранённую запись старого.

Последние уточнения: ошибка «Не удалось отправить» возникает при отправке нового
файла через «Сеть» и воспроизводится в обоих режимах. Ранее успешная отправка
проходила через Happ с другим профилем. Поэтому её нельзя считать подтверждением
работоспособности отправки через «Сеть». Записи ошибок в VPN исчезли. Название
приложения пользователь сохраняет приватным; оно не требуется для сравнения.

На VPS пользователь скачал 8 МиБ с нейтрального HTTPS-сервера Cloudflare отдельно
по IPv4 и IPv6: оба запроса вернули HTTP 200, все 8 388 608 байт и exit 0.
Тот же тестовый файл скачался в браузере Android при полном режиме VPN. Последний
тест использовал домен с двумя семействами адресов и не доказывает выбор IPv6
браузером. Эти результаты подтверждают передачу данных по проверенным путям,
но не доступность сервера загрузки конкретного приложения.

`TestSelectiveIPv6FileTransfer` проверяет отправку случайного файла 8 МиБ,
скачивание всех байтов и два параллельных HTTP Range-запроса к настоящему IPv6
HTTPS-серверу через клиентские обработчики и VLESS/XHTTP/REALITY. Проверены
HTTP/1.1, HTTP/2 и HTTP/3 (QUIC), адресное разрешение и доверие всему приложению.
QUIC проходит настоящий NAT с параметрами клиента и `NewPacketConnectionEx`;
локальные UDP-сокеты заменяют только пакетный канал приложения. Все шесть
сценариев прошли с `-race`, без прямых попыток и без ошибок VPN. Нативный Android,
его определение владельца сокета, TUN/gVisor и внешний сетевой путь эта проверка
не моделирует. QUIC-назначение использует динамический порт локального теста;
особенности внешнего UDP/443 этим не проверяются. Общая неисправность передачи
таких файлов не воспроизведена.

Отсутствие `vpn_issues` не доказывает успешность скачивания: любой ответ, включая
HTTP-ошибку или начало неполного ответа, подтверждает получение данных, а обычный
EOF после полученных байтов не считается транспортным сбоем. VPN не расшифровывает
прикладной TLS и не проверяет HTTP-статус, длину или целостность файла.

## Сравнение с рабочим профилем Happ

Сравнивалась только структура предоставленного профиля. Его credentials и
адреса серверов не сохранялись в коде или отчёте, соединения с ними не открывались.

| Параметр | Happ | «Сеть» в проверенном main |
| --- | --- | --- |
| Канал до VPN-сервера | VLESS / TCP / REALITY, Mux | VLESS / XHTTP / REALITY |
| UDP/443 | `xudpProxyUDP443: reject` у семи основных выходов | Отдельного запрета нет |
| Восстановление домена | HTTP/TLS/QUIC sniffing, `routeOnly: false` | Восстановление из FakeDNS; обычный буквальный IP остаётся IP |
| Прямые маршруты | Есть для `.ru`, category-ru, private и ряда служебных потоков | Доверенное приложение и полный режим используют VPN |
| Выход и DNS | Другие серверы, балансировка, несколько DoH | Собственный VPS и разрешение доменов на его стороне |

Запрет UDP/443 относится к основным Mux-выходам Happ. У мостового выхода этого
параметра нет, прямые маршруты также отличаются. Нельзя утверждать, что любая
успешная отправка в Happ обязательно прошла по TCP через основной VPN-выход.
`queryStrategy: UseIP` не отключает IPv6. Sniffing может заменить буквальный IP
доменом и изменить последующий выбор адреса, но фактическое назначение неизвестно.

Пользователь проверил копию профиля Happ с заменой семи значений
`xudpProxyUDP443` с `reject` на `allow`: отправка нового файла также работает.
Замена не воспроизвела сбой и ослабляет эту гипотезу. Это не доказывает, что
приложение использовало QUIC или основной Mux-выход: протокол и фактический
выход отправки неизвестны. Исходная строка ошибки была TCP.

Пользователь также проверил удаление `domain:ru` и `geosite:category-ru` из
доменного правила маршрутизации в `direct`, сохранив `geosite:private` и
остальные настройки предыдущего теста: отправка продолжает работать. Прямое
исключение этих доменов не оказалось необходимым для успешной отправки Happ.
Это не подтверждает фактическое использование QUIC, конкретный выход балансировщика
или IPv6: этих данных по-прежнему нет.

Следующая изолированная проверка — изменить `sniffing.routeOnly` с `false` на
`true` у обоих входов Happ (`socks` и `http`). При сохранённом sniffing домен
по-прежнему участвует в маршрутизации, но обычный IP назначения не заменяется
найденным в HTTP/TLS/QUIC доменом. В предоставленной конфигурации FakeDNS не
указан. Остальные параметры рабочего профиля остаются прежними. Если отправка
перестанет работать и восстановится при возврате `false`, замена назначения
оказывается существенной для данного пути; это ещё не доказывает дефект Android
или недоступность IPv6 вообще. Пользователь предпочёл прекратить ручное
переключение профиля; эта проверка не выполнена. Дальнейшая работа продолжилась
на локальных воспроизводимых сценариях.

Более точное сравнение клиентов требует подключения Happ к тому же VPS по
VLESS/XHTTP/REALITY с согласованными DNS и назначением. Сейчас у клиентов разные
выходы. В проверенном коде нет готового экспорта профиля для Happ: общая ссылка
`linevpn://` содержит bootstrap API, а не VLESS UUID устройства. Нельзя просто
подменить IP в стороннем профиле. Секреты существующих устройств не читались,
новые устройства не регистрировались, ключи не менялись.

Семантика параметров сверена с [документацией Xray Mux](https://xtls.github.io/config/outbound.html)
и [sniffing](https://xtls.github.io/config/inbound.html), а запрет UDP/443 — также
с исходниками закреплённой в репозитории версии Xray. Эти сравнения не послужили
основанием для изменения DNS, маршрутов или настройки UDP/443 в «Сети».
Сборка APK и изменения рабочего профиля «Сети» в рамках этого сравнения не выполнялись.

## Подтверждённый обрыв ответа после отправки

Найден отдельный воспроизводимый дефект: после чистого EOF входящего TCP-потока
`NewConnectionEx` вызывал `tracked.CloseWrite`. Соединение `core.Dial` закреплённой
версии Xray не реализует `CloseWrite`, поэтому обёртка вместо завершения только
записи вызывала полное `Close`. Это прерывало чтение ответа сервера.

Минимальный тест отправляет файл по IPv6, проверяет получение всех байтов
сервером, завершает только запись приложения настоящим TCP FIN и затем разрешает
серверу вернуть подтверждение. До исправления прямой путь проходил, VPN-путь
возвращал ноль байт вместо 15 360 байт подтверждения. Перед передачей файла сервер
уже успел отправить начальный ответ: отсутствие новой ошибки в UI в таком случае
не подтверждает успешность отправки.

Исправление сохраняет чтение после чистого EOF, если транспорт не поддерживает
half-close. Ошибка копирования, TCP reset или ошибка поддерживаемого `CloseWrite`
по-прежнему полностью закрывают поток. Политика маршрутизации не меняется.

`TestTCPUploadHalfCloseLifecycle` проверяет ответ после FIN, отмену контекста,
смену режима, таймаут бездействия и reset. Есть минимальная конфигурация Xray
и полный локальный VLESS/XHTTP/REALITY; назначение — IPv6 loopback. Прямой
контроль отдельно проверяет штатное поведение native TCP. Прямой dialer запрещён
во всех VPN-сценариях. Две прежние фикстуры round trip с `net.Pipe` теперь явно
отменяют завершённый тестовый запрос: один только EOF отправки больше не означает
отмену ответа. Проверка быстрого завершения при отмене сохранена.

Это не добавляет недостающую возможность передать TCP FIN через VLESS/Xray:
протоколы, которым для формирования ответа нужен именно удалённый EOF, остаются
отдельным ограничением. При молчащем сервере поток сохраняется до существующего
таймаута Xray, отмены или изменения политики. В тесте таймаут уменьшен до секунды;
значение production не менялось. Тест не доказывает, что неизвестное приложение
использует этот сценарий, и не заменяет проверку нового APK на Android.

При подготовке полного теста обнаружилось, что первый REALITY handshake может
ждать пятисекундный цикл определения свойств локального TLS-target. Пятисекундный
дедлайн новой фикстуры был недостаточен и обрывал начальное подключение, ещё до
передачи файла. При закрытии listener во время этого handshake race detector
также обнаружил гонку send/close в зависимости `github.com/xtls/reality`
(`tls.go:559,566`). Дедлайн установления тестового соединения увеличен до 15 секунд,
клиент закрывается перед сервером; проверки времени жизни ответа не ослаблены.
Гонка зависимости не исправлена этой правкой и остаётся ограничением аварийного
завершения handshake.

Итоговая проверка `bash scripts/check.sh go` прошла: форматирование, целостность
модулей, все Go-тесты с `-race -tags with_gvisor` и `go vet`. В ней прошли все
10 сценариев half-close, предыдущие HTTP/1.1/2/3-проверки файлов и расширенная
проверка private egress. Отдельный запуск того же нового XHTTP-теста с исходными
`client.go`/`tunnel.go` через Go overlay воспроизводит исходный отказ:
`upload FIN closed the response direction before the receipt`.
Таким образом, проверено исправление конкретного дефекта, а не только успешность
теста в новой версии. Native Android и релизный APK не проверялись.

## Дополнительные строки TCP/853 и UDP/443

`172.29.255.2:853` адресует виртуальный DNS клиента, который обслуживает обычный
DNS на порту 53, но не TLS-сервис на 853. `192.168.0.1:853` — частное назначение,
часто домашний DNS/маршрутизатор. Серверный `PublicOnly` отклоняет оба адреса до
создания исходящего сокета; это проверяется расширенным
`TestPublicOnlyRejectsSpecialAddressesBeforeSocketControl` на портах 443 и 853.
Открытие private egress или перевод доверенного приложения напрямую не требуется.

Такие строки совместимы с пробами DNS-over-TLS: автоматический режим Android
может проверять порт 853 сетевого DNS и при недоступности использовать обычный
DNS. По одним строкам нельзя установить режим Android или доказать, что DNS
приложения целиком не работает. Подмена назначения DoT публичным сервером без
учёта проверяемого TLS-имени не является корректным общим исправлением.
Описание автоматической проверки 853 приведено в
[документации Google Public DNS для Android](https://developers.google.com/speed/public-dns/docs/using#android).

Два отказа UDP/443 к публичным доменам могут относиться к QUIC, но журнал содержит
только сетевой протокол и порт, не распознанный протокол приложения. Поддержка
HTTP/3 именно этими внешними серверами и доступность пути с VPS не установлены.
Обычный HTTPS по TCP не проверяет UDP/443. В «Сети» нет правила, запрещающего
UDP/443, а локальная передача HTTP/3 проверена отдельно. Название приложения
берётся из Android UID исходной пары сокетов, домен — из FakeDNS; название
REALITY-target не подставляется в эти строки. Проверка конкретной атрибуции на
телефоне не выполнена. Эти записи не доказывают отказ IPv6: в них частные IPv4
и доменные имена без указания выбранного сервером семейства адресов.

Использованные пользователем команды проверки:

```sh
ip -6 route get 2606:4700:4700::1111
curl -q -6 --noproxy '*' --connect-timeout 5 --max-time 10 -I https://one.one.one.one
```

Эти команды проверяют маршрут и независимое HTTPS-назначение через IPv6,
не раскрывая исходный сервис и не изменяя настройки сети.

Адрес взят из [документации Cloudflare](https://developers.cloudflare.com/1.1.1.1/ip-addresses/),
ключи curl сверены с [официальной справкой](https://curl.se/docs/manpage.html).
