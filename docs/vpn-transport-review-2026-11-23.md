# Ревью VPN-транспорта по внешним материалам — 23 ноября 2026

Проверенная база: `main` на `7ba5dc060a77ced1ba45705cafb28bf0703dbdb9`.
Отдельно проверено совместное применение с PR [#39](https://github.com/jEUGENEdev/vpn/pull/39)
на `0111bc4a4768d98b6ec9631a57c849e4a7f18c03`.
Область: DNS, обновление клиентского транспорта, серверный egress и читаемость
генераторов Xray. Это целевое ревью, а не заключение о безопасности всего продукта.

## Исправленные сценарии

| Сценарий | Причина | Изменение и доказательство |
| --- | --- | --- |
| Некоторые имена не разрешаются при большом DNS-ответе | И desktop, и Android игнорировали аргумент `network` в `net.Resolver.Dial`: после UDP-ответа с TC открывался ещё один UDP-сокет | Общий `transport.DirectResolver` соблюдает выбор TCP/UDP и применяет тот же socket control. Локальный DNS-сервер возвращает TC по UDP и ответ по TCP. До исправления: UDP=2, TCP=0, ошибка разрешения; после — успешный ответ через TCP |
| После изменения SNI, порта, адреса сервера, публичного ключа REALITY, short ID или XHTTP path клиент остаётся со старым транспортом | `Sync` проверял ревизию правил и UUID, но не остальные параметры транспорта; серверная конфигурация не обязана менять ревизию аккаунта | `Sync` сравнивает генерируемый `ClientConfig`, как и `applyProfile`. Все шесть параметров проверены с неизменной ревизией, при включённом и выключенном VPN. Проверены сохранение профиля, закрытие старых защищённых потоков, сохранение прямого потока и отсутствие повторного применения неизменной конфигурации |
| Непубличные IPv6-назначения доходят до попытки создания исходящего сокета | `IsGlobalUnicast` не означает глобальную маршрутизируемость; в локальном denylist отсутствовали четыре специальных префикса, также принималась зона интерфейса | Добавлены `2001:db8::/32`, `3fff::/20`, `100:0:0:1::/64`, `5f00::/16`; адреса с zone отклоняются. TCP/UDP-тесты показывают отказ до socket control. До исправления control вызывался; тестовый control запрещал фактический выход в сеть |

DNS-рефакторинг сначала сохранил прежнее UDP-поведение, чтобы интеграционный тест
воспроизвёл именно ошибку протокола. Исправление внесено после красного результата.
Тесты обновления транспорта также сначала падали на старой логике.
Для дополнительного egress-теста старая `policy.go` была подключена через Go
`-overlay`: ошибка воспроизведена без изменения рабочего исправления.

Специальные IPv6-префиксы сверены с
[IANA IPv6 Special-Purpose Address Registry](https://www.iana.org/assignments/iana-ipv6-special-registry/).
Контракт DNS dialer сверён с [Go net.Resolver](https://pkg.go.dev/net#Resolver).

## Структура кода

- `internal/transport/config.go` содержит генерацию клиентской и серверной
  конфигурации. Вложенные блоки VLESS/XHTTP/REALITY развернуты в читаемый вид;
  содержимое конфигурации, порядок outbound и default deny сохранены.
- `internal/transport/resolver.go` заменяет две одинаковые платформенные
  реализации. Ошибка Android protect/interface bind не игнорируется ни для UDP,
  ни для TCP.
- Список egress-префиксов разобран один раз при старте, а не на каждом соединении.

## Сохранённые границы

Прямой DNS применяется только там, где маршрут уже разрешён как direct.
Защищённые домены по-прежнему разрешаются на стороне VPN; ошибки DNS не дают
им прямой резерв. Полный режим из #39 сохраняет свой DNS через туннель.

Смена транспорта закрывает старые защищённые потоки и увеличивает `routeEpoch`.
Повторный неизменный sync не перезапускает соединения. Выключенный VPN остаётся
выключенным, но обновлённый профиль сохраняется для следующего включения.

SPKI и срок сертификата, запрет redirect, отзыв обоих credentials, блокировка
неизвестных Fake-IP и запрет private/metadata egress сохранены. Новые права,
секреты, scanner exceptions и зависимости не добавлены.

## Диагностика при повторении сбоя

1. Проверить отдельно доступность API и передачу данных через VPN. Успех sync
   не доказывает работоспособность канала данных.
2. Сопоставить SNI, публичный ключ, short ID, порт и XHTTP path профиля с сервером.
   Новый sync должен сохранить актуальные значения без изменения правил доступа.
3. Для ошибки прямого DNS проверить UDP-ответ с TC и следующую TCP-попытку;
   отказ socket protection должен завершать запрос ошибкой.
4. Менять MTU/SNI/transport только после подтверждения причины на нужной сети.
   Не включать постоянные журналы с трафиком/секретами ради общей диагностики.
